## Первый приоритет — многоязычный переключатель

### R16 — Выбор языков и языковые пакеты: приоритет №1, реализация не начата

Цель: поддерживать расширяемый набор языков, из которого пользователь выбирает
активные. Например, отключить иврит и включить арабский. Язык интерфейса
остаётся независимой настройкой. R16 идёт первым в очереди разработки;
статусы открытых рисков R01–R05 и критерии No01 при этом сохраняются.

Этапы:

1. **Единый реестр языков на существующих RU/EN/HE.** Собрать идентификаторы,
   названия, флаги, варианты Windows-раскладок, пути словарей, confidence,
   правила алфавита/нормализации и приоритеты в одно описание вместо дублирования
   по модулям. Сначала получить прежние решения на прежних входных данных;
   транспорт замены и работающие Scintilla/RichEdit-пути сохранить.
2. **Выбор активных языков.** Отдельная настройка с исходным набором RU/EN/HE
   для старых профилей. Отключённый язык исключается из автоматического выбора
   и ручного цикла. Согласовать прямые горячие клавиши и отображение флагов.
   Проверять наличие нужной раскладки Windows, учитывать её варианты;
   самовольно устанавливать раскладки нельзя.
3. **Пакеты данных и совместимость профиля.** Определить версионируемый формат
   пакета: код языка, поддерживаемые раскладки, словарь и confidence, метаданные,
   источники и лицензии. Проверять размер, структуру и безопасные пути;
   пакет не выполняет код. Обобщить личный словарь, кэш и упаковку дистрибутива.
   Перед изменением формата профиля — полная проверенная резервная копия;
   личные слова, исключения и настройки RU/EN/HE сохраняются.
4. **Первый новый язык.** Подключить один язык как проверку расширяемости.
   Кандидат — арабский; окончательный выбор и источники словаря согласовать
   перед подключением. Проверить алфавит, нормализацию, диакритику, соответствие
   физических клавиш символам и возможный ввод нескольких символов одной клавишей.
5. **Приёмка и дальнейшее расширение.** Проверить автоматический выбор,
   ручной цикл, горячие клавиши, флаг, исключения, перезапуск и перенос профиля
   при разных активных наборах. Следующие языки добавлять через тот же механизм,
   проверяя их особенности; ввод через IME требует отдельной оценки.

Критерии завершения R16:

- При исходном наборе RU/EN/HE сохраняются прежние решения и работающий ввод.
- Активный набор сохраняется и восстанавливается; отключённый язык не участвует
  в распознавании. Дополнительный пакет не меняет язык интерфейса.
- Первый дополнительный язык работает через общий реестр и пакет, без новой
  жёстко зашитой ветки в каждом модуле. Неполный пакет или отсутствующая раскладка
  дают понятное сообщение; прежний рабочий профиль не повреждается.
- Миграция личных данных проверена на копиях. Модельные тесты дополнены отдельной
  приёмкой настоящего ввода по критериям No01; одно наличие словаря её не заменяет.

## Надёжность и ближайшие проверки

### R01 — Совместимость ранней замены: частично готово

Есть отдельные пользовательские подтверждения ChatGPT, Notepad++ с продолжением
`приветик ` и Блокнота на нескольких языках. Общая совместимость не принята.

- Проверить быстрый ввод, Backspace, удержание клавиши, границы слов, следующее
  слово, смену поля/HKL, Undo/Redo и отсутствие пропавших/повторных букв на обоих ПК.
- Повторно проверить проблемный Блокнот, браузерные поля, Windows Settings/Electron
  и Total Commander после последних правок; старые удачные попытки не закрывают матрицу.
- RichEdit, Scintilla, ручной цикл и клавиатурные замены используют worker после
  выхода из callback. Остаток — физическая надёжность очереди и смены фокуса,
  а не прежняя задача переноса этих операций из hook.
- При неопределённой записи карантин/отложенное раннее исправление остаются защитным
  поведением. Проверить восстановление после реального таймаута, включая закрытие
  Undo-группы Scintilla; модель не подтверждает её фактическое закрытие в зависшем редакторе.
- В обычной сборке нет независимого надёжного обнаружения потери Windows hook
  и автоматического восстановления. Возможность восстановления требует отдельной оценки.
- Уточнить название порогов и документацию `suggest_early`/`suggest_live_early`:
  комментарий про production policy и общий `MIN_EARLY_LENGTH = 5` вводят в
  заблуждение относительно живого пути. Уверенное полное слово от четырёх букв
  уже разрешено действующей политикой и девятью модельными тестами live-пути;
  префиксы и редкие полные слова требуют пяти. Не менять рабочее поведение
  на пять букв только ради имени константы; согласовать комментарии и проверки.

Критерий No01 остаётся **BLOCKED**; подробная приёмка ниже.

### R02 — Первое слово после смены поля: частично исправлено

Общий UIA guard отключён. Пропущенный префикс восстанавливается только из
проверенного EDIT/RichEdit/Scintilla. Для браузерных и неизвестных полей без
надёжного чтения первое слово может пропускаться. Проверить быстрый ввод сразу
после клика/смены поля; исправлять один непроверенный хвост слова нельзя.

### R03 — Частичная отправка и восстановление: частично исправлено

Проверенная однократная досылка остатка есть. SendInput подтверждает принятие
событий Windows, а не итоговый текст/каретку/HKL приложения. Требуется проверка
результата там, где чтение доступно; общий надёжный Undo/автооткат не реализован.
После смены поля ранее удержанные клавиши могут остаться недоставленными.
Ручной возврат ограничен проверенным исходным HWND/процессом/HKL, сроком буфера
и ревизией поля; для браузера один HWND не означает тот же HTML-элемент.
Не повторять принятые части, не переносить ввод в новое поле и не восстанавливать
старый снимок поверх изменившегося документа. Проверка R03 входит в No01.

### R04 — Парольные поля и приватность: отложено, защита неполная

**Известное ограничение P0 экспериментальной alpha-ветки остаётся открытым.**
`PasswordFieldGuard` существует в исходниках, но не подключён к `LiveHook`.
Проверки Win32 EDIT с `ES_PASSWORD` и исключения известных менеджеров паролей
не обеспечивают надёжного определения парольного поля браузера или custom-контрола.
Автоматическое/раннее исправление, ручная конвертация и шаблоны могут изменить
секретный ввод. В Diagnostics при отдельно включённой записи слов он может попасть
в журнал; отсутствие этих модулей в Public не предотвращает ошибочную замену.

Для возвращения защиты нужна проверка конкретного элемента и повторная проверка
перед записью без ожидания UIA в клавиатурном callback. Проверить переходы между
полями с общим HWND, `unknown`, все команды замены и пропуск физических клавиш
без задержек. Не возвращать прежний guard без такой проверки. История буфера
и дневник имеют независимые ограничения; см. [PRIVACY.md](docs/PRIVACY.md).

**Пробел в тестах подтверждён 28 октября.** `test_word_recovery.py` вручную
добавляет `password_guard` и подменяет `hook.context` обёрткой либо `lambda: None`.
Эти проверки моделируют отказ/старый компонент и не доказывают интеграцию защиты
с настоящим `LiveHook`. Явно отделить/переименовать legacy-проверки; добавить
интеграционный сценарий настоящего конструктора и `context()` с подставными
Win32/UIA-границами, без запуска hook и без подмены решения контекста.
Проверить `password`, `unknown` и переход в обычное поле. До реализации боевой
связи отмечать проверку R04 как не пройденную, а не выдавать зелёные компонентные
тесты за защиту паролей. Это не поручение включить прежний guard.

### R05 — Пользовательская проверка дополнительных функций: неполна

Проверить прямые сочетания, цикл Pause, CapsLock, флаг каретки в веб-полях,
импорт, восстановление личного словаря, чистую вставку/историю, автозапуск
и визуальную локализацию RU/EN/HE. Быстрый поиск из Notepad++ подтверждён
пользователем; другие редакторы и восстановление всех форматов буфера ещё не приняты.

**Шаблоны с переносами/табуляцией:** риск действия вместо текста не устранён.
Unicode CR/TAB внутри шаблона приложение может интерпретировать как отправку
сообщения/формы или переход в другое поле; разделитель Enter/Tab отправляется
как физическая клавиша. Нужны проверки в реальных приложениях и отдельное решение
о семантике вставки/Undo. Вынос шаблонов из callback этот риск не решает.

## Распознавание языка и словари

### R06 — Контекст для коротких неоднозначных слов: не реализовано

Например, выбирать `ye → ну` в русской фразе и сохранять `ye` в английской.
Определить достаточность контекста и его сброс при смене поля, каретки и ручного
языка. При недостатке данных сохранять ввод; безусловный приоритет русского не вводить.

### R07 — Числовой частотный арбитраж: отменён, не планируется к возврату по умолчанию

Прежнее правило «не менее 2 на миллион и превосходство 20×» удалено из рантайма.
Текущий выбор использует словарную допустимость, confidence и приоритет альтернатив
RU/EN/HE. `frequency_*.tsv` при запуске не читаются; файлы и инструменты подготовки
сохранены для воспроизводимости/исследований. Не выдавать их наличие за работающий
частотный выбор и не возвращать отменённую эвристику при других исправлениях.

### R08 — Качество и источники словарей: частично сделано

Открытый русский набор строится из FrequencyWords и форм Лебедева/Hunspell;
английский и ивритский — из FrequencyWords/OpenSubtitles. Поставляемые словари
не равны проверенной орфографической базе и могут давать неоднозначности.
Оценить Hspell/обновляемые HE-источники, современные написания и имена; проверять
подтверждённые пропуски без снижения общего порога ради одного слова.
Уже внесённые дополнения и карантин HE-записей не являются универсальной очисткой.
Исторические локальные исследовательские RU/EN-списки не распространяются;
источники и ограничения описаны в [THIRD-PARTY.md](THIRD-PARTY.md).

### R09 — Дополнительные языковые сигналы: обсуждено, не реализовано

Windows Spell Checking API и нетипичные сочетания букв — возможные вспомогательные
сигналы, а не самостоятельное доказательство неверной раскладки. Сначала оценка
качества на примерах. Это отдельная работа над распознаванием, независимая
от транспорта замены; сохранить работающий однозначный выбор.

## Дополнительные возможности

### R10 — Выделенный текст: конвертация/добавление слова не реализованы

Добавить преобразование выделения с выбором смены/сохранения языка и добавление
личного слова/исключения из выделения. Работающий поиск выделения не равен этим
функциям; архивные заготовки требуют проверки перед подключением.

### R11 — Пропустить только текущее слово: не реализовано

Согласовать действие с ранним исправлением, Pause, Backspace и следующим словом.

### R12 — Обучение после отмен: не реализовано

Надёжно отличать ручную отмену/исправление от обычного ввода; затем согласовать
счётчики, настройки и исключения после повторных отмен. Не менять словарь молча.

### R13 — Дополнительные исправления: не реализованы

Двойной пробел, `ТАкое`, таблица орфографии, разделители чисел/времени;
для шаблонов — переменные, форматирование и единый Undo. Сейчас шаблоны содержат
только текст и не выполняют команды. Расширения согласовывать отдельно.

### R14 — Словари узких специальностей: частично готово

Импорт отдельных слов есть, включая исправление длинных строк в исходниках
28 октября. Медицинские/юридические наборы ещё не приложены. Импорт не обрабатывает
синтаксис языка, правила Hunspell или CSpell.

### R15 — Сборки и следующий публичный выпуск: alpha.6 выпущена

Локальные Public/Diagnostics обновлять по обычным путям из одного чистого коммита,
сохранять личный профиль и сверять манифесты сборок. Публикация следующего ZIP — отдельное согласованное действие
через существующий workflow: чистый коммит, полный unittest-набор на открытых данных,
source/frozen self-test, проверка Public EXE, архивов, лицензий, манифестов и SHA-256.
Diagnostics и личные файлы не публикуются. Windows-подписи пока нет.
Альфа-выпуск с раскрытыми ограничениями не означает приёмку стабильной версии.

## Дополнение к аудиту 28 октября

R16 сохраняет первый приоритет разработки. Ниже — новые подтверждённые
замечания; они добавлены в план, реализация не начата.

### R17 — Отдельный поток горячих клавиш буфера/поиска: P1, не исправлено

`ClipboardHotkeys.configure()` устанавливает дополнительный `WH_KEYBOARD_LL`
на потоке трея, если включены соответствующие функции. На этом же потоке
выполняются обращения к Explorer и смена HKL через SendMessageTimeout до 250 мс.
Устранение синхронных запросов из GUI не устраняет эту общую очередь.
Само наличие проблемы потока подтверждено кодом; реальную задержку ввода
и факт удаления hook в этих сценариях ещё не измеряли.

- Вынести обработку hook на отдельный поток с минимальным callback и собственной
  очередью сообщений; Shell, меню и тяжёлые операции выполнять вне этого потока.
  Сохранить пропуск исходных событий в исключённых/неизвестных приложениях.
- Определить наблюдение живучести и безопасное восстановление. Ненулевой handle
  не доказывает наличие hook; прямого надёжного запроса о его удалении нет.
  Не считать 300 мс универсальным порогом: он зависит от LowLevelHooksTimeout,
  а Windows 10 1709+ ограничивает его сверху 1000 мс. См.
  [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).
- Проверить потерянный KEYUP: модель подтвердила, что устаревший `suppressed`
  подавляет следующее нажатие до отпускания даже при пустых bindings.
  Обработать зависшее подавление без повторной отправки уже принятых клавиш
  и без утечки повторов сочетания после отключения функции.
- Приёмка: блокировка/перезапуск Explorer, медленная смена HKL, включение/выключение,
  исключения, удержание клавиш и пропуск KEYUP. Не устанавливать новый глобальный
  hook и не посылать тестовый ввод без отдельного разрешения.

При обычном запуске Pillow создаёт иконки до установки этого hook; саму генерацию
на старте не считать доказанным зависанием уже установленного hook.

### R18 — Безопасность резервного Copy и завершение поиска: открыто

- **Консоли:** резервный путь поиска посылает Ctrl+C. Если пользователь отключил
  категорию исключения IDE/терминалов, отдельного запрета этого fallback нет;
  сочетание может прервать команду вместо копирования. Выбрать независимую
  проверку консольного поля/процесса или иной безопасный способ. Сохранить
  разрешённое чтение выделения через UIA и не расширять запрет на все редакторы.
  [Семантика Ctrl+C в Windows Console](https://learn.microsoft.com/en-us/windows/console/ctrl-c-and-ctrl-break-signals).
- **Завершение:** `busy` сбрасывается в `receive()`; ошибка `Thread.start()`
  воспроизведённо оставляет его `True`, блокируя следующие запросы. Нужны
  сброс при отказе запуска/доставки результата и общий срок запроса, включая
  резервное копирование: шесть секунд ограничивают только UIA-процесс.
- Обработать поздний результат через идентификатор запроса/поколение так, чтобы
  он не снял `busy` у новой операции. Сохранить строгую проверку URL, проверки
  поля/пароля, предпросмотр и запрет повтора Ctrl+C после неопределённой отправки.
- Проверки — на подставных API/консолях; не посылать Ctrl+C в рабочий терминал.

### R19 — Приватное копирование из дневника: P3, не исправлено

`JournalWindow.copy()` явно переносит расшифрованный текст в обычный системный
буфер через Tk без признаков запрета истории/облачного буфера. Это действие
пользователя, а не автоматическая выгрузка, но после него DPAPI текст не защищает.

Согласовать защищённую команду копирования: выставлять системные признаки
запрета истории/облака и исключения мониторинга, учитывать собственную историю
TypeBridge, ясно обозначить выход текста из зашифрованного дневника.
Не обещать защиту от всех сторонних менеджеров буфера, которые могут игнорировать
эти признаки. Проверить форматы и отказ занятого буфера на подставных API;
живой буфер проверять только по разрешению пользователя.

## Остаток аудита быстродействия

Здесь сохранены номера последнего аудита, а не номера R01–R19.

- **№6 — мышиный hook: измерение начато, причина реальных задержек не установлена.**
  Есть изолированный ctypes-замер с подставным CallNextHookEx, без установки
  WH_MOUSE_LL, и счётчики `mouse_max_us` / `mouse_slow` для будущей Diagnostics.
  Они не измеряют ожидание GIL до входа в Python. Архитектура hook и интервал GIL
  сохранены; нужны метрики реального сценария перед изменением маршрута кликов.
  См. [MOUSE-TIMING-RU.md](docs/MOUSE-TIMING-RU.md).
- **№5 — дневник: Python-перебор устранён, SQL-проход остался.** На синтетической
  базе 20 000 записей `_prune` сократился с 26,8 до 5,0 мс. Это замер только
  очистки, не всей записи/DPAPI/fsync и не доказательство задержек компьютера.
  Дальнейшая оптимизация нужна при подтверждённой нагрузке; формат и гарантии
  хранения сохранять.
- **№8 — запуск:** `--onefile` и Pillow остались. Перед переходом к другой упаковке
  измерить распаковку/импорты и холодный запуск. Проверяемый кэш словарей уже есть;
  прежняя полная подготовка при каждом запуске не является открытой задачей.
- **№10 — индикатор/MSAA:** влияние на производительность Chrome не измерено.
  Провайдер каретки уже изолирован в отменяемом процессе; сам факт MSAA-запроса
  не доказывает включения полного дерева доступности или замедления браузера.

Исправления аудита №1–4, №9 и №11 отражены в changelog. Их повторная реализация
не нужна; наличие в конкретном EXE проверяется по исходному коммиту его манифеста.

## Границы текущих возможностей

- **Ранняя коррекция:** уверенное полное слово от четырёх букв, однозначный префикс
  от пяти; полное однозначное редкое слово от пяти при включённой опции редких слов.
  Конкурирующий префикс блокирует ранний выбор. Scintilla ограничена UTF-8,
  документом 64 КБ и одной обычной кареткой.
- **Флаг каретки:** системная/Scintilla/MSAA-каретка; при неизвестных координатах
  флаг скрывается. За мышью не следует. Отдельный процесс не доказывает отсутствия
  нагрузки на обслуживающее приложение.
- **Буфер:** 30 текстов в памяти, до 100 000 символов каждый и 1 000 000 суммарно.
  Чистая вставка убирает HTML/RTF. История не читает буфер без определяемого владельца;
  явная чистая вставка такого текста доступна. Нельзя надёжно распознать каждый
  скопированный секрет по текущему фокусу или системной метке приватности.
- **Поиск:** UIA либо Ctrl+C с предпросмотром и восстановлением поддерживаемых
  форматов до 8 МБ/64 форматов; связанные/встроенные OLE могут не поддерживаться.
  Сторонний менеджер буфера может увидеть копирование. Отправка — только по команде.
- **Дневник:** снимки поддерживаемых нативных редакторов раз в 2 секунды до 64 КБ;
  браузеры не поддерживаются. Хранение 1–365 дней (исходно 7), до 50 МБ/20 000 снимков.
  Запрос выключения отменяет дальнейшие снимки; интерфейс подтверждает выключение
  после уже начатого commit. Старые записи сохраняются, автоочистка работает
  при выключенной записи. DPAPI привязан к Windows-пользователю и не переносим
  как читаемый дневник на другой компьютер/учётную запись.
- **Импорт:** UTF-8 TXT/JSON до 2 МБ/50 000 записей, отдельные слова из 1–80 букв.
  `std::vector` и другие составные токены не разбираются как код.
- **Исключения:** точные имена процессов; исходно включены IDE/терминалы и творческий
  софт. Неизвестные программы добавляются вручную; кэш не расширяет распознавание.
- **Профиль:** папка рядом с EXE должна быть доступна для записи; автозапуск включается
  отдельно на каждом ПК. UI-язык не устанавливает Windows-раскладки. Восстановление
  повреждённого личного словаря требует подтверждения и проверенной полной `.bad`-копии.

## Критерии приёмки R01–R03

1. Исправление и смена HKL происходят до пробела при непрерывном вводе;
   нет пропавших, переставленных или повторных символов, хвост не обгоняет замену.
2. Меняется только отслеженное слово в прежнем поле. Перед записью проверяются
   контекст, каретка, граница и исходный префикс там, где доступно чтение.
   Выделение, readonly/password, смена поля, мышь, вставка, ручной язык и IME
   должны отменять операцию при потере уверенности. IME/режим замещения ещё
   не приняты как поддерживаемые сценарии.
3. Отказ до записи не должен терять обычную клавишу. После неопределённой записи
   нельзя слепо воспроизводить слово или переносить накопленный ввод в новое окно.
   Проверенная досылка остатка из R03 не является повтором принятой части пачки.
4. Проверены удержание клавиши, Backspace, модификаторы, немедленный пробел,
   следующее слово, ручной цикл, CapsLock, шаблоны и Undo. Собственные инъекции,
   подавленные keydown/keyup и физический хвост учитываются раздельно.
5. Отправленные события не равны подтверждённому документу. Даже наблюдение
   последнего собственного keyup не доказывает результат; нужны доступное
   чтение текста/каретки/HKL либо явно обозначенная граница доказательств.
6. Смена фокуса после части удалений может защитить новое окно, но оставить
   старое поле частично изменённым. Запрет записи в новое окно не обеспечивает
   атомарность. Не восстанавливать старый снимок поверх изменившегося документа.
   Внешний hook, съевший события, и завершение с неподтверждённым хвостом требуют
   отдельных сценариев; исследовательский стенд не решает их автоматически.
7. Буфер не используется для посимвольной автокоррекции, исключения сохраняются.
   Выключение экспериментального флага возвращает прежнюю маршрутизацию;
   отказ нового транспорта не должен отключать исправный путь Notepad++.

Если при смене поля/частичной записи нельзя сохранить перехваченный ввод,
такой сценарий не считается принятым. Нельзя устранять отказ сменой фокуса
без разрешения или объявлять отсутствие потерь по одному успешному API-вызову.

### Способы замены и границы расширения

Распознавание в `incremental_recognition.py` отделено от доставки; не менять
одновременно словари, пороги и транспорт. Экспериментальный общий путь использует
`early_correction` и `early_native`, второй флаг исходно выключен.
Нативная маршрутизация опирается на возможности поля, не на коллекцию имён EXE.
Прямой RichEdit-путь ограничивает запись печатными BMP-символами, 64 символами /
256 байтами, проверяет дедлайн и контекст между сообщениями. Эти ограничения
не являются общими лимитами всех текстовых функций.

| Способ | Роль и ограничение |
|---|---|
| Scintilla / NativeEdit | Проверяемая замена и чтение результата в поддерживаемых полях; сохранить работающую базу |
| SendInput | Общий клавиатурный путь; порядок в пачке не гарантирует документ, единый Undo или поведение хвоста |
| UI Automation | Метаданные/чтение, если доступны; TextPattern не редактирует, SetValue не заменяет безопасно участок документа |
| TSF | Возможное отдельное исследование, если общий ввод не выдержит критерии; не готовая универсальная замена и не текущая миграция |
| Буфер | Явный поиск/вставка пользователя; не запасной транспорт автоматического исправления во время набора |

### Фоновые стенды и ограничения запуска

Команды для отдельной проверки доставки из корня проекта; сами по себе
не доказывают физический ввод или качество словарного выбора:

```powershell
python -m unittest test_early_native_edit test_early_keyboard_probe -q
python early_native_harness.py --self-test
python early_native_harness.py --runtime-self-test
python early_keyboard_native_probe.py
```

Нативные стенды используют отдельные процессы и неактивный объект Windows
desktop на том же компьютере, без VM и воздействия на пользовательский desktop.
WM_CHAR/сообщения контрола не заменяют реальную SendInput-очередь.
Исторические отчёты стендов в `build/` не являются текущей приёмкой.

`early_live_trial.py` и `keyboard_transport_trial.py`
нужны только для отдельного разрешённого опыта в собственном пустом поле.
Открытие само по себе не включает hook; включение стенда и SendInput — уже
вмешательство во ввод. Перед опытом исключить конкуренцию с основным TypeBridge,
после — закрыть стенд и проверить снятие hooks. `--accept-injected` относится
к автоматизированному вводу стенда, не к изменению политики рабочего приложения.
Рабочие документы стендами не проверять. Локальная страница
`fixtures/keyboard-probe.html` содержит text/search/textarea/contenteditable/password;
её наличие не доказывает поддержку браузера, снимок не возвращает пароль.
