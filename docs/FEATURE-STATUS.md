# TypeBridge: что работает и что на очереди

Обновлено 23 октября 2026 года. Это текущий список; старые статусы в
архивных отчётах относятся к прежней реализации и не являются текущей приёмкой.
Нумерация сохранена из каталога SwitchER. Объём V1 — исходные пункты 01–13.

## Рабочая контрольная точка

После установки нового раннего режима пользователь сообщил: «знаешь вроде
работает». Это первая успешная пользовательская проверка раннего исправления
в предложенном сценарии Notepad++; конкретные слова, направления, темп и Undo
пользователь отдельно не перечислял. Не считать это полной приёмкой No01.

Копия установленного EXE и текущих исходников:
в локальном архиве `working-early-checkpoint-20261022` (в репозиторий не входит).
35 файлов сверены по SHA-256; манифест `SHA256-MANIFEST.json`.
Это копия EXE/исходников/основных документов, не полный дистрибутив со словарями,
Python-зависимостями и личными настройками. Словари остаются в рабочей `data/`.
Ранний механизм не менять без конкретного воспроизводимого дефекта либо
отдельного решения расширить поддержку. Следующие функции добавлять отдельно.

## Уже доступно

- Автоматическое исправление RU/EN/HE на границе слова.
- Пробное исправление до пробела в Notepad++; первая проверка пользователя
  успешна. Строчные буквы, UTF-8 Scintilla, документ до 64 КБ, одна обычная
  каретка; по умолчанию отдельная галочка выключена. При отключении исправление
  выполняется после завершения слова (пробел или другой разделитель): анализ
  целого слова может снизить риск преждевременных ошибочных исправлений и
  не использует экспериментальный механизм ранней замены.
- Ручной цикл последнего отслеженного слова по Pause, выбор клавиши,
  сохранение регистра и окружающей пунктуации. Пока подтверждено модельными
  проверками; отдельного пользовательского отчёта о цикле нет.
- Настраиваемая клавиша словарного исправления набираемого слова до пробела; по умолчанию Scroll Lock.
- Личные слова и исключения RU/EN/HE: добавление, удаление, сохранение,
  применение к работающему движку без перезапуска; галочка «Учитывать регистр»
  задаёт точное написание для нового слова или исключения.
- Равнозначный поиск е/ё во встроенных русских словарях; обработка «а»/«и».
- Флаг текущего языка в трее; выбор настроенной Windows-раскладки из меню.
- **№26: флажок возле текстовой каретки.** В трее добавлен пункт с галочкой
  «Флажок у текстового курсора»: сразу включает/скрывает индикатор, сохраняет
  только эту настройку и синхронизирует флажок на вкладке «Индикация».
  Добавлен независимый отключаемый
  индикатор RU/EN/HE: вкладка «Индикация», галочка и «Сохранить настройки».
  По умолчанию выключен. Работает и при выключенном/остановленном автоисправлении.
  Источники координат: системная каретка Windows, API Scintilla для Notepad++,
  MSAA-каретка для приложений, которые её предоставляют. При неизвестных,
  устаревших или находящихся вне поля координатах скрывается. Положение мыши
  вместо текстовой каретки не используется. Окно не активируется и пропускает
  клики; учитываются границы рабочей области монитора и DPI.
  Проверены настройки, геометрия, COM ABI, скрытие и нативное скрытое окно;
  повседневное отображение в пользовательских полях ещё не подтверждено.
- Прямые сочетания RU/EN/HE на вкладке «Горячие клавиши»: по умолчанию
  Ctrl+Shift+F1/F2/F3; выбор/ввод своего сочетания либо отключение. Меняют
  только раскладку, работают также на паузе при запущенном движке. Проверяются
  внутренние конфликты с другими языками, клавишами исправления/перебора слова и Ctrl+Alt+Pause.
- Включение/пауза автоисправления в трее, Ctrl+Alt+Pause, сохранение настроек.
- Исключения по именам процессов, ограничение по заголовку окна, защита
  нативных Win32 password-полей, один рабочий hook, остановка и выход.

Наличие функции в приложении не означает физической проверки во всех редакторах.

## Исключения приложений — категории и пропуск горячих клавиш

- Отдельное окно «Исключения приложений…»: обязательные хранители паролей,
  отключаемые категории «IDE и разработка» и «Графика, видео и звук», личный список `.exe`.
  Обе профессиональные категории включены по умолчанию, в том числе при чтении
  старых настроек. Явно отключённые категории сохраняются отключёнными.
- IDE: VS Code/Insiders, VSCodium, Cursor, Windsurf, Visual Studio, IDE JetBrains,
  Android Studio, Sublime Text; терминалы Windows Terminal, cmd и PowerShell.
  Творческие программы: Adobe, Resolve/Fusion, Blender, Maya, 3ds Max, AutoCAD,
  REAPER, FL Studio, Studio One, Pro Tools, указанные версии Cubase/Nuendo.
  Это списки точных имён процессов, а не автоматическое распознавание всего
  профессионального софта. Все имена видны в окне, незнакомые можно добавить вручную.
- Исключения действуют на автоисправление, ручные команды, сочетания буфера и
  сбор его истории. Учитываются процесс активного поля и процесс окна-хоста.
  В неизвестном/недоступном контексте клавиши передаются приложению.
- Ctrl+Alt+Pause перенесён после проверки исключений. Двойной Shift специально
  не перехватывался; Ctrl+Break не назначен команде по умолчанию.
- У команд буфера убрана глобальная регистрация RegisterHotKey: отдельный
  обработчик проверяет активное приложение до перехвата. При выключенных
  функциях не устанавливается; поздние отпускания уже перехваченных клавиш
  завершаются без повторного запуска команды. Обработка независима от состояния
  автоисправления. Ctrl/Alt сбрасывают незавершённое слово, исключая устаревшее
  состояние после вставки.
- Проверены настройки/миграция, пропуск команд, фильтрация окна/дочернего процесса,
  модель обработчика и скрытый интерфейс. Живая проверка в IDE ещё не выполнена.

## Буфер обмена — базовая реализация по отдельному запросу

- Новая вкладка «Буфер обмена»: история и чистая вставка включаются независимо,
  обе по умолчанию выключены и работают независимо от автоисправления.
- История: 30 последних текстовых фрагментов, до 100 000 символов каждый,
  суммарно до 1 000 000 символов; одинаковые записи перемещаются наверх.
  Только память, без файлов и логирования содержимого. При отключении и выходе
  список очищается; при включении учитываются только новые копирования.
- Отдельное окно из трея или Ctrl+Alt+H: просмотр, удаление, очистка,
  копирование и вставка выбранного фрагмента в исходное окно. Кнопка вставки
  явно возвращает фокус; при изменившемся/закрытом целевом поле вставка отменяется.
- Чистая вставка: Ctrl+Shift+V; доступны изменение сочетаний и отключение.
  Буфер заменяется выбранным Unicode-текстом, HTML/RTF не восстанавливаются.
  Обычный Ctrl+V не перехватывается. Переносы строк/табуляция передаются через
  штатную вставку приложения, раскладка не меняется.
- Исключённые процессы и известные отметки приватности не попадают в историю.
  Полная защита секретов не заявлена: не все программы отмечают приватный текст.
- Проверены модель, настройки, конфликты, очистка, отмена при смене поля,
  транзакция буфера и интерфейс в скрытом режиме. Живая вставка, Undo и работа
  с форматированным текстом в целевых редакторах требуют пользовательской проверки.

## План V1: что остаётся

### Быстрый поиск — локальная сборка для проверки

После пользовательской проверки первой общей сборки: галочка поиска отображалась
включённой, но в личном файле оставалось выключенное состояние. Причина пока не
установлена; автоматизация окна была отклонена инструментом доступа. Добавлены
явный статус сохранения, проверка записанного файла и видимая диагностика ошибок
Tk-обработчиков (`ui-errors.log`: тип исключения и строки кода, без сообщений,
содержимого переменных, выделения или URL). Сохранение через реальный обработчик
во временном профиле проверено без пользовательского ввода и глобальных hooks.

- Отдельное окно «Быстрый поиск…»: независимый флажок включения (исходно выключен),
  выбранный поисковик, добавление/редактирование/удаление сервисов и словарей.
  Пример — Google; HTTP/HTTPS URL содержит единственную метку `{query}`.
- Горячая клавиша по умолчанию Ctrl+Alt+G; можно выбрать/ввести другую или
  отключить. Конфликты с языковыми и буферными командами отклоняются.
- Сначала читает одно выделение до 2000 символов через Windows UI Automation.
  Внешний помощник запускается скрыто, с ограничением 6 секунд. Для подтверждённо
  отсутствующего TextPattern добавлен общий Ctrl+C с восстановлением всех
  поддерживаемых форматов буфера (до 8 МБ / 64 форматов) и предпросмотром перед
  отправкой. Новое чужое содержимое не перезаписывается. Непереносимые native-handle
  форматы отменяют резервный путь до копирования. Парольные, пустые и неизвестные
  UIA-ошибки не включают fallback; исключённые приложения пропускаются.
  Резервный путь общий, без привязки к Notepad++ или другому редактору. Некоторые
  приложения без выделения копируют строку, поэтому отправка требует подтверждения.
  История TypeBridge приостанавливается, сторонние менеджеры могут увидеть Copy.
- Текст URL-кодируется; поиск открывается в обычном браузере только по команде.
  При смене целевого окна, настроек или завершении приложения результат отменяется.
  Выделение и URL не добавляются в диагностический журнал. Запрос может
  сохраняться в истории браузера и у выбранного сервиса.
- Проверены настройки, фильтрация URL, кодирование RU/HE, конфликты, маршрутизация
  клавиш с поддельным Win32 API, отмена, скрытое окно и локализация RU/EN/HE.
  Синтаксис помощника и наличие UIA API проверены без чтения активного окна.
  Всего 55 узких проверок поиска, локализации, горячих клавиш и исключений прошли.
  Физическая проверка выделения и запуска браузера ещё не выполнялась.

Пользовательская проверка общей сборки: сочетание дошло до обработчика, но UIA
не предоставил выделение Notepad++; это не ошибка отсутствующего выделения у
пользователя. В ответ добавлен описанный общий резервный путь. Модельные проверки
подтверждают восстановление форматированных данных, отмену при смене поля/буфера,
отсутствие отправки до подтверждения и работу предпросмотра RU/HE/EN. Универсальная
совместимость со всеми приложениями не заявлена; живой повторный тест ещё нужен.
46 узких проверок поиска, буфера, локализации и диагностики прошли; настоящий
Ctrl+C и открытие браузера в пользовательском приложении автоматикой не выполнялись.
Новая локальная сборка подготовлена по обычному пути `dist/TypeBridge.exe`,
включает общий резервный путь и диагностику сохранения. Публичный релиз не заменён.

Следующая пользовательская проверка выявила отказ до копирования: прежний буфер
содержал изображение и служебные OLE-форматы `DataObject` / `Ole Private Data`.
Они больше не блокируют резервную копию и не восстанавливаются как сырые указатели:
сохраняются материализованные форматы данных. Настоящие встроенные/связанные OLE-
объекты остаются отдельным ограничением. 13 узких проверок прошли. На текущем
пользовательском буфере резервная копия успешно создана только на чтение: bitmap,
PNG, DIB/DIBV5 и флаги приватности, около 1 МБ; владелец и sequence не изменились.
После установки пользователь подтвердил: предпросмотр появляется, поиск в браузере
открывается. Это подтверждение основного пользовательского сценария в Notepad++,
не всех редакторов и не побайтовой проверки восстановления каждого формата буфера.

### Предыдущий этап: раннее исправление в RichEdit

Проведён анализ текущего разделения распознавания и замены. План и критерии
сохранности ввода: [EARLY-CORRECTION-EXPANSION.md](EARLY-CORRECTION-EXPANSION.md).
В основной обработчик подключён общий экспериментальный транспорт, исходно
выключенный. В настройках нужно включить «Исправлять до введения пробела» и
«Раннее исправление в других приложениях (эксперимент)», затем сохранить.
Оба значения сохраняются; старые настройки новый путь не включают.
Работающий Scintilla-путь Notepad++, правила распознавания и словари сохранены.
Для проверки доступны: `early_native_edit.py`, фоновый
нативный стенд `early_native_harness.py` и ручной стенд `early_live_trial.py`.
Проверка идёт по возможностям поля RichEdit50W, без списка адаптеров EXE.
В отдельном неактивном Windows desktop подтверждены шесть направлений замены,
каретка после Unicode/переноса строки, сохранность окружающего текста,
синтетическое продолжение и отказ при выделении. Буфер обмена не используется.

**Дефект Undo на иврите исправлен в отдельном транспорте:** вместо
EM_REPLACESEL выбранный диапазон заменяется штатными WM_CHAR с границами
EM_STOPGROUPTYPING. COM/TOM-группировка удалена: неограниченных COM-вызовов
в этом пути больше нет. Нативный стенд подтверждает 6/6 направлений, Undo/Redo,
отдельный Undo продолжения и восстановление полного исходного слова.
Физический ввод не проверен; браузеры, Windows Settings и Electron не подключены.
63 узких проверки прошли: новый путь, старый runtime Notepad++, настройки и
локализация. Основной обработчик с настоящим движком и нативным RichEdit в
другом процессе прошёл 6/6 направлений до пробела, разделитель и два сценария
следующего слова (`early_native_harness.py --runtime-self-test`). Это фоновая
симуляция доставки WM_CHAR, без глобальных hooks и SendInput, не физический ввод.
Ошибка/таймаут нового пути отключает только его, не ветку Notepad++.
Неподдерживаемые поля сохраняют прежний путь на границе слова.
Собран `dist/TypeBridge.exe`, его фоновый `--self-test` завершился с кодом 0.
Новый режим в EXE выключен по умолчанию; программа автоматически не запускалась.
Предыдущий EXE сохранён в `build/pre-native-integration-596356e/`.
Подробности и запуск стенда:
[EARLY-CORRECTION-EXPANSION.md](EARLY-CORRECTION-EXPANSION.md).
После разрешения пользователя проведён также видимый автоматизированный тест
через Computer Use: RU→EN с продолжением, EN→RU и RU→HE исправились до пробела.
Первый тест воспроизвёл потерю исходного слова при Ctrl+Z для иврита.
После исправления видимая проверка подтвердила `флгщ → שלום → Ctrl+Z → флгщ`
и `Ctrl+Y → שלום`. Это автоматизированный ввод, не физический набор и не
проверка быстрого потока. Стенд закрыт, hooks сняты. Остаётся допуск по
физическому вводу и совместимости полей. По просьбе пользователя дальнейшие
проверки в этом шаге выполнялись только в фоне, без новых живых окон.

### Общий клавиатурный способ — подключён к основной программе

По прямому решению пользователя выбран простой практический путь: для остальных
полей `LiveHook._try_keyboard_early` использует тот же `correction_inputs` и
SendInput, что обычное исправление после разделителя. Удаляется только уже
доставленный префикс (`len(keys)-1`), вставляется всё исправленное слово без
пробела, текущая клавиша подавляется. Это не новый движок и не адаптер браузера.
Пути Notepad++/Scintilla и RichEdit сохранены; прочие приложения больше не
отбрасываются из раннего режима по классу поля. Исключения приложений сохранены.

Включение: обе галочки «Исправлять до введения пробела» и «Раннее исправление
в других приложениях (эксперимент)», затем «Сохранить настройки».
При нулевом возврате API обычная клавиша проходит, блокируется только текущее
слово (другие приложения не отключаются); при частичном — новый путь
отключается до перезапуска, нет повтора/слепого отката, для нечётного count
отправляется только cleanup keyup. Смена поля перед отправкой отменяет операцию.
Статус SendInput — отправка команды, не подтверждение текста чтением из поля.

62 узкие проверки прошли: прежний ранний режим, новый общий путь, нативная
маршрутизация и локализация. Для общего пути модель проверяет 6/6 направлений,
продолжение, разделитель, следующее слово, смену поля и нулевой/частичный count.
Собран основной EXE; новая возможность сохраняет существующий opt-in флаг
`early_native=false` по умолчанию. Программа автоматически не запускается.
Старый EXE: `build/pre-keyboard-fallback-b2aab7c/`.

Пользователь подтвердил раннюю замену `ghbdtn → привет` и продолжение до
`приветик ` в поле ChatGPT в браузере; ранняя замена также сработала в Notepad++.
В обычном Блокноте пользователь воспроизвёл пропуски даже после разделителя.
Фоновое наблюдение обнаружило разные HKL у главного окна и дочернего поля.
Попытка всегда использовать главное окно для чтения и смены HKL дала регрессию:

## Предлагаемая очередь — ещё не разрешение на реализацию

1. **Выполнено по запросу пользователя: точный регистр для личного
   слова/исключения (№10/11).** Скрытая GUI-проверка с временным словарём
   подтвердила добавление, чтение с диска, различение регистра и удаление.
2. **Выполнено по запросу пользователя: прямые сочетания RU/EN/HE (№04).**
   Проверены настройки/миграция, внутренние конфликты, точные модификаторы,
   повтор клавиши, работа на паузе и отказ при изменившемся фокусе.
   Пока проверено модельно, без живого переключения пользовательского окна.
3. **Пропуск только текущего слова (№13).** Полезно против ложного исправления,
   но нужно согласовать жизненный цикл с ранней заменой, Pause и Backspace.
4. **Автозамены №07/08: базовая реализация готова по запросу пользователя.**
   Следующий шаг — пользовательская проверка шаблонов; затем **выделение №03**.
   Архивный код выделения требует проверки перед подключением.

Двойной пробел кажется маленькой функцией, но затрагивает тот же поток ввода и
границы слов. Автообучение меняет решения автоматически. Их не брать первыми,
если приоритет — сохранить уже работающий переключатель.

### Запланировано: язык окружающего текста для коротких слов

Статус: **не реализовано**, добавлено по запросу пользователя 23 октября.
При настоящей словарной неоднозначности учитывать язык окружающей фразы:
например, `ye → ну` в русском контексте, сохраняя `ye` в английском.
Это отдельный механизм распознавания, а не удаление допустимых английских слов
или безусловный приоритет русского. Нужны правила достаточности/сброса контекста
при смене поля, перемещении каретки и ручном выборе языка; при недостаточном
контексте сохранять ввод. Реализацию и проверку спроектировать отдельно от
работающего раннего переключения.

Обсуждённые дополнения пока **не реализованы**: частотное сравнение неоднозначных
кандидатов с порогом значимого преимущества; невозможные сочетания букв как
дополнительный сигнал; Windows Spell Checking API как возможный источник
проверки. Нужны отдельные правила и проверка качества; действующий выбор
однозначного словарного кандидата ради новых вспомогательных функций не менялся.

Подтверждённые примеры: `nfr → так` конкурирует с HE `מכר` в обеих базах;
`rjt → кое` в локальной базе конкурирует с HE `רחא`; `zvc → זהב` в локальной
базе конкурирует с RU `ямс` (в открытой базе исправляется). `rfr → как` выбирается
движком после разделителя, пользователь подтвердил успешное исправление.
До пробела любые трёхбуквенные слова остаются вне текущего раннего режима.
