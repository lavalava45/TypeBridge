# R04 — проверка адресного RichEdit на неактивном Windows desktop

**04.11.2026. Статус: native synthetic evidence; R04 OPEN, No01 BLOCKED.**

## Сфера и ограничения

- Проверка выполнялась на **текущем Windows-хосте** в отдельном
  **неактивном Windows desktop**, НЕ в виртуальной машине. Два
  одноразовых поля A и B — `RichEdit50W` со своими HWND, в
  самостоятельно созданных тестовых окнах; A принадлежит дочернему
  тестовому процессу, B — вызывающему тестовому процессу.
- Только синтетические `SendMessageTimeoutW`, `WM_CHAR`, `EM_SETSEL`,
  `EM_UNDO`, `EM_REDO`, `WM_GETTEXT`; в транзакции используется
  существующий `NativeEditBridge` с **явно включённым только в тесте**
  `experimental_target_lease=True`.
- Не использовались глобальные hooks, `SendInput`, физическая клавиатура,
  пользовательский буфер обмена, оригинальный SwitchER64, пользовательские
  файлы/пароли, активация desktop, смена пользовательского foreground/
  фокуса/HKL, VM или реальные приложения. Установленный TypeBridge не
  запускался и не изменялся. **Ни одного физического перехода фокуса
  A→B не выполнено.**
- Для детерминированного тайм-аута кратко приостанавливался **только
  GUI-поток специально запущенного дочернего тестового процесса**,
  с гарантированным `ResumeThread` в `finally`. Пользовательские
  процессы и потоки не приостанавливались; проверено завершение
  дочернего процесса после каждого прогона.

в каждом дочерний процесс после проверки завершился.

## Результаты реальных Windows-сообщений

| Проверка | Фактический результат |
|---|---|
| Базовый существующий NativeEdit harness | `range_checks_ok=true`, 6 сценариев RU/EN/HE, `undo_restores_source=true` во всех шести |
| Нативный ручной цикл | 3 подтверждённые замены; несовпадающее исходное слово отвергнуто |
| Два длинных слова, off-hook | 2/2 с восстановлением Undo |
| Исследовательский одиночный `EM_REPLACESEL` | RU: текст и Undo успешны; **HE: текст успешен, Undo не восстановил исходное слово**; не применять его вместо текущего `WM_CHAR` |
| Адресный NativeEdit `ghbdtn → привет` | A = `привет`, B = `B_UNCHANGED`, Undo вернул `ghbdtn`, Redo вернул `привет` |
| Адресный NativeEdit `akuo → שלום` | A = `שלום`, B неизменен, Undo/Redo корректны |
| Адресный NativeEdit `руддщ → hello` | A = `hello`, B неизменен, Undo/Redo корректны |
| Тайм-аут через **настоящий `NativeEditBridge.msg`** при приостановленном тестовом GUI-потоке A | `TimeoutError`; `native:preflight:message-102:error-1460`; `timeout=True`, `write_started=True`; B неизменен; автоматически не повторялось |
| Содержимое A после возобновления потока | `T` (в этих запусках поздний символ не наблюдался). **Это не гарантия**, что сообщение после тайм-аута никогда не будет обработано |
| Уничтожение окна A перед следующим `WM_CHAR` | `ValueError:window-closed` **до следующей отправки** через opt-in TargetLease; B неизменен |
| Три повторных прогона адресного теста | 3/3 PASS, 5/5 случаев в каждом, ошибка 1460 воспроизведена 3/3, тестовый процесс завершился 3/3 |

В тестах **не было переключения настоящего фокуса A→B**. Адресность
подтверждается тем, что каждое изменяющее сообщение направлялось
по первоначальному HWND A, после чего выполнялся Win32-readback обоих
отдельных контролов. Это проверка реального адресного транспорта, но не
всех возможных гонок Win32.

## Что доказано, а что нет

**Подтверждено настоящими Win32 API на disposable контролах:**
нынешний NativeEdit + opt-in TargetLease выполняет адресную замену,
readback, Undo/Redo на трёх примерах RU/EN/HE, не изменяя независимый
RichEdit B. При уничтоженном до новой отправки A проверка отказывает.
При специально заблокированном получателе timeout действительно
отмечается неопределённым, и повтор не выполняется.

**Не доказано:** фактическая гонка смены фокуса внутри сообщения,
повторное использование числового HWND в настоящем Windows,
невидимая смена DOM-поля внутри общего browser HWND,
атомарность пачки `WM_CHAR`, отсутствие поздней доставки *во всех*
тайм-аутах, целостность Undo/Redo при произвольной длине и настоящем
редакторе, физический ввод и задержанная очередь, реальное переключение
HKL, универсальная защищённость парольных полей и No01.
Отдельный модельный контрпример с HWND reuse по-прежнему воспроизводит
ложно успешную проверку. `SMTO_ERRORONEXIT` — не блокировка жизни HWND.

## Следующая узкая задача

Рассмотреть отдельный эксперимент, различающий повторное создание
контрола с тем же HWND и безопасную жизненную идентичность в рамках
доступных Windows API. Не включать opt-in режим в живой `LiveHook`,
не менять fallback или настройки по умолчанию и не утверждать, что
браузерная R04 решена. Для браузерного DOM-поля понадобится
объектно-адресный механизм либо доказуемое узкое ограничение конкретного
случая — без расширения браузера.
