# R10: падение Notepad++ при Pause — 07.11.2026

## Причина подтверждена

Пользователь выделил слово и дважды нажал Pause. В Windows Application
зафиксированы два падения Notepad++ 8.9.8.1: 11:16:46 и 11:17:16,
exception `0xc0000005`, offset `notepad++.exe+0x278b4f`.
Дампы `notepad++.exe.13048.dmp` и `notepad++.exe.33092.dmp` находятся в
пользовательской `AppData/Local/CrashDumps`. Исследованы только exception,
регистры, стек и машинные инструкции, текст документов не извлекался.

В стеке второго дампа видна команда `0x872 = 2162 = SCI_GETTEXTRANGE`.
Падение произошло на записи завершающего нуля по адресу
`0xfffffff003290010`.

TypeBridge передавал 16-байтовый legacy header: два 32-битных LONG
и 64-битный указатель. В Scintilla, поставляемой с Notepad++, typedef
`Sci_PositionCR` изменён на `intptr_t`: получатель читает 24-байтовый header.
Поля смещались: выделение `[0,16]` превращалось в начало `0x1000000000`,
конец — в адрес нашего output buffer `0x3290010`, указатель текста — в NULL.
Разность границ даёт ТОЧНО адрес записи из дампа:
`0x3290010 - 0x1000000000 = 0xfffffff003290010` modulo 64 bits.

Источники: [Notepad++ Sci_Position.h](https://github.com/notepad-plus-plus/notepad-plus-plus/blob/v8.9.8/scintilla/include/Sci_Position.h),
[Scintilla FULL API](https://www.scintilla.org/ScintillaDoc.html#SCI_GETTEXTRANGEFULL).

Это ошибка адаптера TypeBridge. Прежние 15 нативных сценариев на DLL Pythonwin
проверяли другой legacy ABI и не подтверждали совместимость с Notepad++.
Старый модельный тест также повторял класс структуры отправителя у получателя,
поэтому мог подтверждать ошибочную договорённость с самим собой.

## Исправление в исходниках

- Используется `SCI_GETTEXTRANGEFULL (2039)` с `Sci_TextRangeFull`: две
  pointer-sized signed позиции и указатель, всего 24 байта в x64.
- Header и payload buffers выделяются с учётом нового размера.
- Отката к `SCI_GETTEXTRANGE (2162)` нет. Неподдерживаемый FULL получает отказ
  до замены; не пытаемся угадывать host ABI опасным pointer-message.
- Тест-получатель независимо декодирует `<qqQ`, не использует структуру
  отправителя. Отдельная регрессия воспроизводит адрес из реального дампа
  арифметически, без запуска ошибочной команды в редакторе.

## Проверки и ограничения

33 узких теста: адаптер (включая ABI и отсутствие legacy fallback), ядро
и реальный обработчик Pause с модельным транспортом прошли.

Прежний private-desktop harness с Pythonwin DLL после исправления отказал
`selection-incomplete-range`: DLL не реализует FULL. Это отказ совместимости,
не успешная нативная конверсия и не новый access violation.

Подготовлен `experiments/r10_private_notepad_full_range_20261107.py`:
запуск установленного Notepad++ в неактивном desktop с отдельным settingsDir,
`-multiInst -nosession -noPlugin`, только собственный disposable PID.
Три попытки остановлены до операций чтения/замены: у тестового процесса
не обнаружены окна редактора за отведённые 10 секунд. Каждый собственный
процесс завершён; пользовательские процессы не закрывались. Причина отказа
такого фонового запуска не установлена; его нельзя считать приёмкой патча.

Пользовательский foreground, HKL, clipboard и физический ввод не менялись.
TypeBridge не останавливался, EXE не пересобирался. Патч требует новой сборки;
уже собранный EXE с legacy header остаётся опасным для этого сценария.

Следующий шаг — проверка исправленной сборки в отдельном тестовом документе
настоящего Notepad++: два Pause подряд, полный цикл и Undo/Redo. Физическая
проверка требует разрешения пользователя; перенос теста в активное окно
автоматически не выполняется. Chrome и остальные release gates остаются открытыми.
