# Win32 `_context()` — точечная оптимизация, 08.11.2026

## Обнаруженная избыточная работа

В `LiveHook._context()` на **каждом** обычном `WM_KEYDOWN` происходили:

1. `GetWindowTextW(top)` с выделением 512-символьного буфера, даже если
   `settings.only_window_title` пуст (фильтр заголовка выключен).
2. `GetClassNameW(focus)` и, если `focus != top`, `GetClassNameW(top)`.
3. `layout_owner()` **повторно** делал `GetClassNameW(top)` и
   `GetClassNameW(focus)` для выбора потока HKL, хотя эти классы уже
   известны вызывающей функции.

Текущая правка: заголовок читается **только** для непустого фильтра,
а `layout_owner()` принимает необязательные исходные классы окон
(`top_class`, `focus_class`), полученные в рамках той же проверки
фокуса. Другие вызовы `layout_owner()` без новых аргументов продолжают
читать оба класса самостоятельно. В `_context()` сохраняются
`GetForegroundWindow`, PID/идентичность процесса, `GetGUIThreadInfo`,
`IsChild`, исключения приложений, проверки класса сфокусированного
контрола, проверки password/UIA в строгом режиме, фактический HKL.
`FocusContext.title` пуст, если фильтр заголовка не используется:
в рабочих путях TypeBridge это поле не читалось.

## Измерения

Измерения на текущем Windows 11, в отдельном Python-процессе,
**без установки hook, синтетической печати, активации окон или
вмешательства в пользовательский ввод**. Вызывался только read-only
`_context()` с реальными Win32 API; замеры обёрток включают Python
instrumentation overhead. В журнал не сохранялись заголовки окон,
содержимое полей или набранные символы.

| Измерение | До | После |
|---|---:|---:|
| Независимые серии: 750 вызовов, медиана | 135,4 мкс | 68,8 мкс |
| Независимые серии: 750 вызовов, p95 | 324,2 мкс | 143,5 мкс |
| `GetClassNameW`, вызовов на 750 контекстов | 2 250 | **750** |
| `GetWindowTextW`, вызовов на 750 контекстов | 750 | **0** |

Результаты независимых серий **не являются достоверным коэффициентом
ускорения**: даже неизменённые Win32 вызовы выполнялись быстрее во
второй серии, что показывает влияние загрузки ОС.

Более корректный дополнительный эксперимент: из `git HEAD` до правки
динамически извлечены исходные функции `_context()` и `layout_owner()`;
старый и новый варианты чередовались в **одном процессе с одним и тем
же настроенным `LiveHook`** (1200 пар вызовов, поровну старый/новый
первым). Код старой версии не записывался в отдельный EXE.

| Парное сравнение | Старый | Новый | Разница |
|---|---:|---:|---:|
| Медиана | 59,4 мкс | 51,2 мкс | −8,2 мкс (−13,8%) |
| p95 | 142,4 мкс | 128,9 мкс | −13,5 мкс (−9,5%) |
| Среднее | 76,2 мкс | 68,0 мкс | −8,2 мкс (−10,8%) |

**0/1200 расхождений** между old/new по
`(top, focus, thread_id, language, hkl, native_target)`.
Парный эксперимент также является микробенчмарком read-only пути, а
**не** p50/p95 полной физической клавиши или видимой коррекции в Chrome.
Он не доказывает поведение всех приложений при смене фокуса.

## Регрессии и границы

`test_context_win32_fastpath_20261108.py` проверяет:

- отсутствие заголовка и повторных классов при выключенном фильтре;
- сохранение case-insensitive фильтра по заголовку;
- отказ до чтения класса/HKL при несовпадении заголовка;
- путь `ApplicationFrameWindow`/`Windows.UI.Core.CoreWindow`;
- одно чтение класса, когда `focus == top`;
- полную обратную совместимость `layout_owner()` для остальных клиентов.

Существующая логика определения процесса, exclusion policy, target admission
и смены раскладки не изменена. Проверять реальную задержку коррекции,
последовательные физические `Pause`, взаимодействие с `Ctrl+Z` и
стабильность фокуса следует отдельно после штатной пересборки на
просьбу пользователя; работающий Public EXE не заменять.
