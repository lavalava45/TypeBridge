## Смена поля после последней проверки

Использован `R04DefaultTargetTests.hooked_context()` с реальным обработчиком
`LiveHook._correct_keyboard()` и `PasswordFieldGuard`. Сначала разрешён элемент
`uia:1,100`. Внутри подменённого `SendInput`, после всех предварительных проверок,

`uia:1,101` с теми же HWND. `revalidate` в этой модели подменён проверкой текущей

Пакет: `ghbdtn → привет` с пробелом, 26 событий. Число принятых событий задаётся

принятие уже после перехода в парольное поле: предварительная проверка не
связывает SendInput атомарно с проверенным UIA-элементом.

## Подтверждённый дополнительный дефект (до правки)

После полной отправки `_correct_keyboard()` вызывает
`_browser_field_changed_after_submission()`. Эта проверка ориентируется на
`_browser_field_revision`. Если поменялись только UIA-метаданные/ревизия guard,
она не останавливает последующий `WM_INPUTLANGCHANGEREQUEST`, хотя новый вызов
`context()` уже отверг бы парольное поле. Это модельно подтверждённый путь
нежелательной смены HKL; изменения реального поля/пароля здесь не проверялись.
