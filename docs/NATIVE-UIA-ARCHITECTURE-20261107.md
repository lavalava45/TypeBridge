# TypeBridge — единый нативный UI Automation worker (07.11.2026)

## Цель

Удалить PowerShell из runtime UIA-путей и запускать не более одного
постоянного COM-помощника. Не выполнять UIA/COM в `WH_KEYBOARD_LL`,
не читать документ целиком, не использовать глобальные Backspace без
независимых проверок TextPattern, не сохранять содержимое полей в логах.

## Выполненная реализация в исходниках

* `uia_native_worker.py`: собственный `multiprocessing` STA worker внутри
  поставляемого Python/PyInstaller EXE, `comtypes` → Windows UI Automation COM,
  один bounded IPC через `Pipe`, единый сериализованный доступ, повторное
  использование процесса. Provider timeout завершает зависшего помощника;
  запросы без разрешённого поля завершаются отказом без SendInput.
* `caret_word_recovery.py`: короткие ограниченные чтения слова из TextPattern,
  два независимых сопоставления выделения, текста, идентичности UIA Runtime ID,
  фокуса, HWND ancestry и IsPassword. Нет нового PowerShell на каждом Pause.
* `password_fields.py` / `uia_password_native.py`: отложенная проверка паролей,
  адресуемости поля и UIA Runtime ID через тот же worker. Native Edit/RichEdit
  проверяется также по `ES_PASSWORD`; браузер не доверяет одному HWND.
* `FocusEventMonitor`: native COM-подписки на UIA FocusChanged и
  IsPassword PropertyChanged, STA message pump. Счётчик событий передаётся
  как восьмое поле metadata. Изменение счётчика отменяет старую ревизию,
  даже если UIA Runtime ID после A→B→A вернулся к прежнему значению.
  При недоступной подписке metadata не выдаётся как safe. Это ещё не
  подтверждено на реальном браузерном COM provider.
* `quick_search.py` / `uia_selection_native.py`: чтение только выделенного
  текста (до 2000 символов) с повторным подтверждением владельца и range.
  Защищённый Ctrl+C fallback разрешён только для достоверного отсутствия
  TextPattern, не при отказе безопасности.
* `browser_readback.py`: необязательная локальная диагностика использует
  тот же COM worker; не входит в Public profile.
* `typebridge_app.py`: для браузера и иных неадресуемых native HWND
  требуется свежий `safe/addressable` UIA metadata sample, включая
  идентичность элемента. При helper unavailable/unknown/password — запрет
  редакторской мутации, физический ввод пропускается.

## Проверка скорости

Отдельный импортируемый исходный smoke-test, без чтения активного UIA поля,
проверил создание COM worker и два неподдерживаемых запроса:

* Холодная активация COM/процесса: 275,8 мс (один раз).
* Повторная IPC round-trip: 0,1 мс.
* PID тот же; helper не перезапускался.

Это не бенчмарк реальных Windows UIA TextPattern запросов и не доказательство
порога 50 мс. Целевая задержка Pause ≤50 мс остаётся **не проверена**.

## Открытые ограничения

1. **Никакая быстрая UIA preflight не делает глобальный SendInput атомарным**.
   Изменение DOM-focus между последним UIA-чтением и доставкой событий всё
   ещё возможно; P0-D/R04 остаются OPEN/BLOCKED.
2. Ранее PowerShell metadata watcher получал события UIA FocusChanged и
   IsPassword. Нативный COM worker теперь тоже подписывается на эти события,
   но доставку callback и message pump **нужно проверить физическим тестом**;
   матрица тестов пока моделирует обработчики. Родитель получает новое
   поколение примерно каждые 100 мс; возможность изменения DOM до
   следующего опроса сохраняется. Равнозначность не доказана.
3. Упаковка `comtypes.gen.UIAutomationClient` в настоящий frozen EXE **проверена**:
   модуль есть в архиве, встроенный self-test проверил импорт COM-типа и
   запуск повторно используемого синтетического IPC child. Это **не** проверяет
   подписки на реальные UIA events/фактический TextPattern Windows.
4. Не проводилась физическая проверка Chrome, Edge или Notepad++ этой версии;
   тесты моделей не означают совместимость с DOM в браузере.

## Chrome regression и исправление — 07.11.2026

Первая нативная сборка отказала во всей автокоррекции браузера: штатный
metadata-only debug.log зарегистрировал `context-rejected:uia-target-unverified`.
Проверка на реальном Chrome подтвердила `unknown/provider-error` до входа в
лексический движок; Notepad++ продолжал работать.

Установлены две ошибки `uia_password_native.PasswordProbe.query()`:

1. `RawViewWalker.GetParentElement()` на конце дерева возвращает ложный
   NULL COM pointer, который **не равен** Python `None`. Проверка
   `ancestor is None` приводила к `ValueError: NULL COM pointer access` при
   следующем чтении свойства; заменена на корректную `if not ancestor`.
2. Chrome вернул `IsPassword=False` у сфокусированного Document-контрола,
   но два промежуточных узла не реализовали это свойство. Требование
   `bool False` у **каждого предка** ошибочно запрещало поле. Теперь
   обязателен явный `False` у самого поля, а все предки проверяются на
   `IsPassword=True`; неизвестное свойство у несвязанного контейнера само по
   себе не отменяет подтверждение сфокусированного поля. Положительный
   `IsPassword=True`, ошибки провайдера, неподтверждённый RuntimeID или
   HWND по-прежнему запрещают замену.

Кроме того, `uia_native_worker` не выдаёт положительную metadata-ревизию,
если при выполнении запроса пришло новое событие фокуса или пароля.

Выполнена **реальная безопасная read-only проверка** (без чтения документа,
клавиш, фокуса или глобального hook): прямой COM PasswordProbe и два запроса
через один постоянно запущенный дочерний `UiaService` вернули
`state=safe`, `reason=checked`, `addressable=1`, валидный Runtime ID и
generation-счётчик; дочерний процесс повторно использован.

После исправлений **155/155 профильных тестов прошли** (модельные и
синтетические). Штатный `build-typebridge.ps1` опубликовал новые:

* Public `dist/TypeBridge.exe`: SHA-256
  `d0395ccfbfd387dbd8612bf6e5d44597b623906d3346d7f63f630387ad40c51d`.
* Diagnostics `dist/profiles/Diagnostics/TypeBridge.exe`: SHA-256
  `082fb8a069ed6e4d9d9d81d574f4af3c1c1b0c8e442135bc9691a1cdf294abe3`.

У обоих успешен frozen self-test 6/6, `uia_helper_ok=true`, оба SHA-256
совпали с манифестами, в Public нет трассировки пользовательского текста.
После публикации новых сборок `TypeBridge.exe` не запускался.

**Не считать физическое автопереключение Chrome доказанным** до очередной
проверки пользователем. Гонки при глобальном `SendInput` остаются открытым
P0-D/R04 риском; не путать с устранённым `provider-error`.

## 07.11.2026 — повторная регрессия Chrome: COM-события и Pause с выделением

Следующая пользовательская проверка выявила повторное чередование
`context-ready`/`uia-target-unverified`, а также `reader-refused` при Pause на
выделенном слове. Выяснено:

* Native UIA STA-child аварийно завершался во время повторной подписки
  `FocusEventMonitor.refresh()` на `IsPassword` property-change. Сгенерированный
  интерфейс comtypes не принимал исходный Python COMObject-параметр при
  `AddPropertyChangedEventHandler` (ошибка `ctypes.ArgumentError`, interface
  `40CD37D4-C756-4B0C-8C6F-BDDFEEB13B50`). Реальный read-only замер
  дал 20 unavailable на 70 запросов. Исправлено на явные COM
  `QueryInterface` pointers и `AddPropertyChangedEventHandlerNativeArray`
  c bounded array; при ошибке регистрации worker возвращает отказ, сохраняет
  процесс и повторяет не раньше чем через 500 мс.
* После исправления **два независимых запуска по 70 metadata-only запросов**
  использовали один дочерний процесс и не дали ни одного падения;
  одна последовательность зарегистрировала реальное изменение поколения
  события фокуса. Проверка без чтения пользовательского текста.
* Старый `read_native_caret` правильно отвергал непустой диапазон выделения,
  но браузерного альтернативного маршрута для команды Pause не существовало.
  Добавлен `selected-word` режим с коротким UIA TextPattern GetSelection,
  повторной проверкой начальной и конечной границ диапазона, runtime/focus,
  affirmative password, generation и одноразовым worker-local COM range lease.
  Только после независимого pre-send verify приложение может отправить
  Unicode-пакет замены выделения без Backspace. Никакой гарантии атомарности
  с DOM это не создаёт: P0-D/R04 остаётся открытым.
* Реальная таблица RU/EN/HE проверена модельно для `ch,` (EN) → `בית` (HE):
  запятая в EN соответствует букве ת на HE; для автоматической замены нужен
  последующий разделитель, например пробел. Токен и целевая словарная запись
  корректны в модельном тесте.
* `transport-quarantine` теперь пишет только безопасный код причины и признак
  локального/global scope в debug pipeline; ранее постоянный статус
  «Автоисправление ограничено» не давал достаточно сведений для точного
  различения `worker-error`, `input-barrier-lost` и неопределённой записи.

**Проверки исходников:** 294/294 профильных теста успешны, `py_compile` и
`git diff --check` успешны. **Сборка:** после проверки отсутствия процессов
TypeBridge штатный `build-typebridge.ps1` опубликовал:

* Public `dist/TypeBridge.exe` SHA-256
  `87f471138863210c101542cba26ff1eb81a6ffa94f5930c87e5da7971def922f`
* Diagnostics `dist/profiles/Diagnostics/TypeBridge.exe` SHA-256
  `5b882c86aef7adbf626c17859870586a48b18f8bc4b6b669e22df33946422faa`

Обе сборки прошли замороженный self-test 6/6, native UIA helper успешно
проверен в обеих сборках, Public не включает текстовые трассы, опубликованные
SHA-256 совпали с манифестами. После сборки активных процессов TypeBridge=0.

**Открыто:** физическая проверка печати и выделения в Chrome на новой сборке;
способность Chrome применять Unicode `SendInput` к выделению и точная причина
возможного нового tray quarantine. Нельзя считать эти исходы доказанными
только unit-тестами и COM metadata-only проверкой.

  HKL RU подтверждён.
* 15:26:42.632 UTC — RU→EN, четыре клавиши, отправка завершена, HKL EN.
* 15:26:46.861 UTC — EN→RU, четыре клавиши, отправка завершена, HKL RU.
* 15:26:49.534 UTC — RU, четыре клавиши, словарный отказ
  `already-valid-source-word`, ожидаемый если на русской раскладке уже
  набрано `глаз`. Полезный вывод: в этом событии слово не было потеряно

Отдельно 15:26:33.801 UTC после полной отправки и подтверждённой смены
раскладки появился `transport-quarantine:input-barrier-lost:scoped=yes`.
Исходный журнал не сохранял точную `gate.aborted_reason`, потому однозначная
причина карантина **ещё не доказана**. Вероятный сценарий: после смены HKL
оригинальный физический KEYUP пробела приходит, когда UIA/context revision
уже отличается; hook раньше сравнивал `_native_scope` перед его перехватом,
в результате без нового текстового ввода мог выставляться `focus-changed`.

**Источник, пока не пересобрано:**

* Добавлена узкая `NativeTransactionQueue.capture_trigger_keyup` для
  единственного ещё не доставленного KEYUP исходного подавленного
  триггера. В app-hook её проверка выполняется до потенциально устаревшего
  сравнения поля. Все обычные клавиши, модификаторы, повторное нажатие,
  аварийное состояние и переполнения остаются под старыми ограничениями.
* Добавлена безопасная диагностика `input-barrier-aborted` с истинной
  причиной отказа, количеством недоставленных событий и индикаторами
  неопределённости — без VK, scan codes, пользовательского текста, PID, HWND.
* `test_notepad_barrier_replay_20261107.py` моделирует изменение HKL между
  подавленным Space KEYDOWN и его KEYUP, исключения для прочих физических
  событий, повторное отпускание и аварийный отказ.
* 133/133 профильных теста прошли, `py_compile` и `git diff --check` успешны.

Установленный `dist/TypeBridge.exe` пока **не содержит** этого дополнения:
во время проверки работали четыре процесса TypeBridge, а `AGENTS.md`
запрещает пересборку до выхода пользователя через трей. Даже после новой
сборки реальную причину карантина нужно подтвердить по safe telemetry;
не обещать устранения до фактической проверки в редакторе.

## Chrome regression: intermittent UIA gate + volatile input recovery

Пользователь повторно сообщил, что Chrome не переключает. Журнал новой
сборки в 14:37 UTC подтверждает, что словарь нашёл EN→RU слово длиной 6,
но сразу после `decision-found` появилась диагностика
`native-job-unavailable:pending-input-recovery`, а не попытка `SendInput`.
То же сообщение встречается при последующих Pause. Обработка слова была
заблокирована ранее отложенным буфером физических нажатий, который создаётся
на случай отмены транзакции до отправки. Буфер не следует автоматически
воспроизводить, сбрасывать без уведомления или переносить в другое поле.

Также зафиксированы чередующиеся `context-ready:app=chrome.exe` и
`context-rejected:uia-target-unverified`. Повторный независимый read-only
тест COM-помощника обнаружил, что его полноценная проверка UIA занимает
обычно около 70 мс (медиана 71,26, p95 86,72 мс на 32 вызовах). Общий
`UiaService` использовал лишь 50 мс ожидания занятого IPC-lock. В модели
двух конкурирующих читателей 6 из 48 вызовов получили отказ из-за lock
contention; старый metadata watcher ошибочно трактовал его как недоступность
провайдера и немедленно заменял `safe` на `unknown`, сбрасывая event epoch.

В исходниках исправлено:

* `UiaService.request(..., on_busy=...)` возвращает отдельный сигнал **только
  при занятости mutex**, не при аварии/timeout/невалидном COM-провайдере.
* `PasswordFieldGuard` при таком сигнале не меняет имеющийся sample, revision,
  event generation или checked_at. Обязательная TTL 500 мс НЕ продлевается;
  после её истечения Chrome по-прежнему отказывается от мутации. Реальный
  отказ сервиса немедленно переводит состояние в `unknown`.
* Для операции чтения каретки вне keyboard hook допускается ожидание
  общего mutex до 125 мс; метаданные по-прежнему ограничены 50 мс.
* При ранее сохранённом буфере input recovery первая повторная попытка
  сообщает пользователю понятную причину блокировки; следующие не спамят
  сообщением. Автовосстановления/удаления клавиш нет.

Профильный тестовый прогон после изменений: **144/144 PASS**; проверка
синтаксиса и `git diff --check` успешны. Физическое исправление автокоррекции
в Chrome **ещё не подтверждено** и эта версия исходников **не пересобрана**:
перед штатным `build-typebridge.ps1` пользователь должен выйти из приложения
через трей, а сборщик подтвердить отсутствие всех процессов TypeBridge.exe.
