## Реализация

Новый `scintilla_selection.py` использует транспорт сообщений/remote-memory
из существующего Scintilla bridge, не меняя его ранний словарный путь и лимиты.

- Reader получает только фиксированный выбранный диапазон через
  `SCI_GETTEXTRANGE`, а не весь документ и не изменяющийся по размеру
  `SCI_GETSELTEXT`. Буферы отдельно ограничены 8000 байтами UTF-8 на данные и
  замену; структура диапазона имеет Windows ABI с 32-битными LONG границами.
  Поэтому этот адаптер пока требует 64-битные процессы и документ не больше
  `INT32_MAX` байт. Весь файл ради выделения не читается.
- Проверяются process/thread/class, UTF-8, один обычный stream-диапазон,
  отсутствие readonly/virtual space и включённый сбор Undo. Обычное выделение
  через несколько строк поддерживается; прямоугольное и множественное — нет.
- Snapshot включает opaque document pointer: смена вкладки/документа при
  прежнем HWND не считается прежним диапазоном. Anchor/caret и текст перечитываются
  перед записью; после замены сохраняются направление и подсветка выделения.
- Запись — один `SCI_REPLACETARGET`. В исходниках Scintilla внутри этого метода
  создаётся `UndoGroup`; не требуется отдельная внешняя пара BEGIN/END, которая
  при тайм-ауте могла бы остаться неподтверждённой. Это согласуется с полученной
  ниже проверкой одной команды Undo для каждой замены.
- После тайм-аута транспорт не позволяет повторно использовать remote-буфер
  и сохраняет его до завершения процесса-получателя, как прежний word-bridge.
  Закрытый транспорт не обращается к освобождённому буферу. Ядро R10 не повторяет
  неопределённую запись и не выполняет слепую отмену.

Первичные спецификации: [Scintilla — выбор диапазона и замена](https://www.scintilla.org/ScintillaDoc.html#SCI_GETTEXTRANGE),
[Undo/Redo](https://www.scintilla.org/ScintillaDoc.html#SCI_UNDO),
[исходник Editor::ReplaceTarget](https://github.com/mirror/scintilla/blob/master/src/Editor.cxx),
[типы координат](https://github.com/mirror/scintilla/blob/master/include/Sci_Position.h).

Нативные сообщения по-прежнему не образуют общей атомарной транзакции с
произвольным кодом редактора. Сохранение документа за пределами диапазона
подтверждено на контролируемом стенде, не во всех гонках внешнего приложения.

## Что действительно запускалось

Использована уже установленная DLL:
`C:/Users/dslava/AppData/Local/Programs/Python/Python312/Lib/site-packages/pythonwin/scintilla.dll`.
Её контрольная сумма сохранена в отчёте; DLL не копировалась в проект и не
распространяется с этим изменением.

Скрипт запускает собственный Python child. Только этот child создаёт private
desktop и два собственных Scintilla-контрола A/B. Главный поток проверяющего
процесса временно привязывается к этому **неактивному** desktop для обмена
сообщениями, не активируя его. Тестовый subclass допускает только точный PID/TID
созданного им child; обычный адаптер сохраняет Notepad++ identity gate.
После проверки все собственные окна/процессы/desktop закрываются.

Нет SwitchDesktop, SetFocus, SetForegroundWindow, SendInput, hooks, clipboard,
переключения HKL или обращения к пользовательским документам. Это не VM.

## 15 нативных сценариев — все прошли

1. Шесть направлений RU/EN/HE × прямое/обратное выделение: 12 сценариев.
   Проверены точный результат, CRLF, TAB, emoji, сохранение выделения и обоих
   соседних фрагментов. Поле B осталось `B_UNCHANGED`. В каждом сценарии одна
   команда Undo восстановила исходный документ; redo вернул результат.
2. Три последовательных цикла на одном выделении с регистром/переносом/emoji.
   После трёх циклов исходная строка совпала точно. Три Undo по одному вернули
   три предыдущих состояния; три Redo восстановили их последовательно.
3. Выделение из 2000 символов, включая 1999 emoji, после префикса 100 000 символов.
   Сам адаптер читал только выделение, не префикс/документ. Замена и одна Undo
   сохранили точный полный текст. Полный документ для проверки читает только
   стенд, и только из собственного синтетического поля.
4. Изменение выделения после подготовки: операция отказала до текстовой записи;
   документ и пустая Undo-история остались неизменными.

**Undo/Redo проверяют восстановление текста.** Восстановление самой подсветки
при Undo/Redo не обещается: подсветка явно сохраняется после нашей замены,
а историю выделения при внешней отмене контролирует редактор.

Дополнительно прошли 19 unit-тестов ядра/адаптера, включая смену document pointer,
readonly/rectangular selection, потерю ответа после записи, ограниченную структуру
чтения, закрытый транспорт и запрет перезаписи буфера после тайм-аута. Модель
потери ответа не выдаётся за настоящий Win32-тайм-аут; живые гонки с вводом и
плагинами редактора здесь не воспроизводились.

## Что осталось

- Подключить этот диапазонный путь к существующей команде вне callback и
  существующей очереди владельца; положительно обнаруженное выделение имеет
  приоритет над словом. После выбранного диапазонного пути не падать обратно
  на пакет Backspace при ошибке/неопределённом исходе.
- Проверить полный Notepad++ с его обработчиками/плагинами, а не только
  Scintilla DLL. Reader/provider для Chrome и других обычных полей ещё отдельная
  работа; эта проверка не закрывает браузерную совместимость.
- Определить источник раскладки смешанного выделения, обработку внешнего
  Undo/смены поля и связь с подтверждённой сменой HKL в live-контроллере.

`typebridge_app.py` в этом этапе не менялся. Сборки, запуска TypeBridge, коммита
и публикации не было; установленный EXE остаётся прежним.
