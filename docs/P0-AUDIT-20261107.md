**Дополнение после исправлений:** P0-A получил проверенный DPAPI checkpoint
перед подменой и явное восстановление из трея; overflow P0-B сохраняет
неотправленные печатные клавиши для ручного возврата. Исправления только в
исходниках, EXE прежний. Частичное состояние clipboard возможно, но его
полная резервная копия сохраняется. Остальные P0 не объявлены закрытыми.
[Исправления, ограничения и следующие проверки](P0-CLIPBOARD-RECOVERY-20261107.md).
Ниже сохранён исходный read-only аудит ДО этих исправлений.

**Статус:** критические риски остаются; R04 OPEN, No01 BLOCKED.
**Метод:** read-only ревизия исходников, сверка SHA-256 с активным
`dist/BUILD-PROFILE.json`, воспроизводимые Python-модели с подменёнными
Win32 API и действующие регрессии. Пользовательские окна, физический
ввод, буфер, HKL, хуки и запущенный EXE не изменялись.

Рабочая ветка `main` на `c5c0950`, но дерево содержит большое
количество незакоммиченных исходников/тестов. Публичный EXE совпадает
с манифестом `abfdba7c16008018b8bb07dced489b8cf2faff949e362eb00ee6c5`.
Дополнительно отдельно сверены SHA-256 *модулей* с исходным
снимком манифеста.
`clipboard_selection.py`, `password_fields.py`,
`native_transaction_queue.py`, `input_transport.py`,

## P0-A — возможная необратимая утрата rich clipboard (подтверждено моделью)

**Код:** `clipboard_selection.py:291–341`, непосредственно
`EmptyClipboard` в строке 328 и цикл `SetClipboardData` в 329–334.
`copy_transaction` вызывает `restore` после временного Ctrl+C
(`clipboard_selection.py:64–117`), также используется при отказе
временного plain paste. Снимок исходных форматов сначала сформирован,
но их восстановление Windows API не атомарно.

**Воспроизведение:** собственный `NativeCopy` с мокированными Win32:
два формата, первый SetClipboardData вернул success, второй — failure.
Получено: `EmptyClipboard_count=1`, затем вызовы Set форматов 13 и
49443, затем `OSError('clipboard-restore')`. Первый формат
восстановлен, второй нет; исходный буфер очищен.

**Классификация:** P0-блокер сохранности пользовательских данных,
условен отказом Win32 во время восстановления. Это **не** случай
повреждения реального пользовательского буфера в тесте.
Простая повторная попытка после частичного изменения также опасна:
первоначальные объекты/владение форматами могли уже измениться.

## P0-B — подавленная клавиша теряется при переполнении native gate

**Код:** `native_transaction_queue.py:79–119`, лимит 256
(`MAX_BUFFERED_EVENTS`); `typebridge_app.py:1399–1588`.
При overflow gate прекращает принимать клавиши и делает
`aborted_reason='buffer-overflow'`. В ветви восстановления
`typebridge_app.py:1535–1558` этот reason отсутствует.

**Воспроизведение:** mock-gate с limit=1 (для детерминированного
переполнения); вызов реального `handle_keyboard` через fixtures:
KEYDOWN A подавлен, следующий B пропущен в Windows, после
`_drain_native_input` `SendInput_calls=0`,
`native_pending_recovery=None`, source quarantined. Исходная
подавленная A не возвращена. Существующий тест
`test_offhook_native...test_buffer_overflow_allows_next_physical_key_and_blocks_new_jobs`
подтверждает это поведение.

**Классификация:** P0 при безусловном требовании отсутствия потерь
физических символов. Реальная частота переполнений при лимите 256
и блокирующих Win32/provider операциях не измерена. Это также
дизайн-выбор «пропустить будущие клавиши вместо зависания hook»,
не означает, что hook бесконечно глушит ввод.

## P0-C — неизвестное парольное поле разрешено выбранной политикой

**Код:** `typebridge_app.py:341–346,749–859,1056–1135`;
`password_fields.py:447–476`. GUI/headless использует
`explicit_password_only=True`: `permit_revision` запрещает
только совпадающее со снимком поле со `state='password'`;
для неизвестного, отсутствующего и устаревшего UIA возвращает
revision, а `revalidate` не запрашивает свежий ответ.
Нативный `ES_PASSWORD` остаётся отдельно запрещённым.

**Воспроизведение:** `test_user_field_policy_20261106` проверяет
настоящие mock-handlers автоматической и ручной коррекции:
при отсутствующих UIA metadata оба пути доходят до замокированного
`SendInput`; при явном `password` событий нет.
Отдельно synthetic Chrome context при пустой UIA metadata выдаёт
не-`None`. Содержимое реального парольного поля не тестировалось.

**Классификация:** осознанная пользователем политика совместимости
от 06.11, **но безопасность R04 P0 остаётся недоказанной**:
провайдер, не распознавший пароль, не способен остановить замену.
Результат нельзя называть новой неожиданной регрессией.
Изменить это универсально без возврата строгого отказа для
некоторых неизвестных полей невозможно.

## P0-D — generic Backspace при устаревшей памяти слова и новом выделении

**Код:** generic Pause `typebridge_app.py:_cycle_word` и
`manual_cycle_inputs`; новый source-only Scintilla R10
решает один узкий вариант, но не браузерные/cross-editor поля.

**Воспроизведение:** `experiments/r10_selection_reuse_audit_20261107.py`,
непосредственный вызов функции `run()` с мокированным
`SendInput` и in-memory текстом. Начало:
`PREFIX ghbdtn SUFFIX`, выделено `ghbdtn`, у приложения осталась
старая память слова. После Pause-замены модель возвращает строку,
не начинающуюся с `PREFIX `: первая Backspace удаляет всё выделение,
следующие удаляют часть префикса. Суффикс сохранён.

**Классификация:** P0 при подтверждённой возможности скрытой
программной смены выделения без события input hook. Не доказано,
что каждый редактор/браузер реализует этот сценарий в живой вкладке.
Текущий рабочий EXE не содержит нового source-only Scintilla adapter.

## P0-E — гонка R04 между проверкой поля и глобальным SendInput

**Код:** `typebridge_app.py:_send_guarded_inputs` и generic
auto/early/manual/snippet callers. Проверки UIA + HWND/revision/HKL
до SendInput и после не фиксируют адресата в момент доставки событий.
Два DOM-поля браузера могут иметь один HWND, а JS фокус может сменить
между проверкой и обработкой очереди ввода. Ни одно из этих сравнений
не делает доставку атомарной.

**Классификация:** P0 security/data-integrity **OPEN**.
Существующие тесты подтверждают некоторые безопасные отказы при
уведомлённой смене поля, но не содержат доказательства отсутствия
перенаправления при произвольной гонке A→B. Поле пароля B особенно
опасно в сочетании с P0-C. Реальный физический браузерный эксперимент
этим аудитом не запускался.

## Приоритет инженерных исправлений

1. **P0-A:** прекратить обещать безусловное сохранение rich clipboard;
   спроектировать безопасный механизм резервирования/атомарного отказа
   для поддержанных форматов, включая ошибку середины SetClipboardData.
   Нельзя исправить только «ещё одним повтором».
2. **P0-B:** спроектировать bounded cancellation/explicit recovery
   первично удержанных printable клавиш при overflow, не направляя их
   в новое поле и не повторяя уже отправленные.
3. **P0-D:** перед generic Pause/Backspace проверять отсутствие чужого
   выделения при доказуемом способе; если оно не проверяется —
   отказаться от разрушительной замены или предложить адресный адаптер.
4. **P0-C/E:** для гарантии паролей нужен более строгий policy gate
   либо реальная атомарная доставка в конкретный DOM-элемент.
   Последний пока не найден. Подмена R04 дополнительной UIA-проверкой
   недопустима; смена default policy требует явного продуктового решения.

**Никаких изменений исходного кода, сборки, Git, пользовательских данных
и настроек в рамках аудита не выполнялось.** Создан только этот отчёт.
