## What the current evidence does **not** establish

1. **Why a particular temporary EXE disappeared.** No pathname, before/after snapshot, creator PID, file-system delete event, or timeline of that file was supplied. A build-stage candidate, an unrelated installer, a user-temp binary or an antivirus-quarantined executable have different owners. `_MEI*` itself is ordinarily a directory of extracted dependencies, not a separate copy of `TypeBridge.exe` at the current executable image path.
2. **That TypeBridge deletes its own EXE or `_MEI` files.** No application-level deletion of `sys._MEIPASS` or `sys.executable` was found in reviewed creation/cleanup paths. This does not exclude code outside the scanned repository, PyInstaller bootloader behavior, Windows cleanup or external software.
3. **That an orphaned `_MEI` is safe to delete.** The one current `_MEI000081782` timestamp aligns with the running onefile process. Historic entries may have unrelated owners. Removal was outside the task and would risk active dependencies or user data.
4. **That the caret child caused deletion.** PID 18984 began much later than the current `_MEI` directory; it shares the canonical EXE path and has the application PID as parent. This supports normal spawn, but causality for disappearing files is not established.

## Instrumentation that could establish the cause in a future authorized reproduction

1. Record a **read-only process timeline** at one-second or event-driven resolution containing PID, parent PID, creation time, image path, process exit time, and role tags (bootloader parent, application child, multiprocessing child, PowerShell helper). Avoid collecting command-line secrets; log only a sanitized role or boolean markers.
2. Log at app startup and caret-worker creation the sanitized `sys.frozen`, `sys.executable` basename/path, `sys._MEIPASS` directory identifier, PID/PPID, helper child PID, `_runtime_health` result and monotonic timestamps. Read only existence of `base_library.zip`/`python312.dll`, never contents. Log before/after `cancel()` with exit code and whether the extracted directory still exists. **Do not add these probes without separate scope approval.**
3. If a disappearing pathname is known, perform a narrowly filtered Windows file-system event capture (for example Sysmon configuration or Process Monitor with explicit path and PID filters) recording `CreateFile`/rename/delete/disposition operations and the actor process. Record metadata only; disable data-buffer capture and exclude private file paths unrelated to this case. Correlate event time with parent/child exits and creation of `_MEI` rather than inferring cause from directory disappearance.
4. Capture build-phase events separately: `verified-typebridge-*` staging creation, candidate hashes, `publish_verified` entry/exit, `os.replace` transitions, rollback, staging-context exit. Use the existing build logs and manifest timestamps for correlation. A candidate disappearing **after** successful publication is normal staging cleanup, whereas removal of installed `dist/TypeBridge.exe` while running would require another explanation.
5. Compare two controlled samples (without touching the user's running program): a future explicitly authorized frozen self-test on an isolated nonactive desktop and a normal launched instance, collecting only lifecycle events. Do not install a second distribution or run real input/hooks as part of this audit.

## Conclusion

The observed process tree and `_MEI000081782` creation time fit the documented PyInstaller **onefile runtime** plus a spawned frozen caret worker. The code independently creates and automatically removes **build staging candidates** under `build/verified-typebridge-*`. These are separate ownership domains. The disappearance of any particular temporary EXE remains **unattributed** without its exact path and a file-system event showing who removed it. No cleanup action is justified by this read-only evidence.
