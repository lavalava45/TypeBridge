# TypeBridge — независимый эксперимент с Windows Spell Checking API

**Дата:** 2026-10-30. **Статус:** исследование завершено; в рабочий движок
изменений не вносилось. **Рекомендация:** использовать только как
опциональное асинхронное подтверждение для неоднозначных / отсутствующих
в словаре случаев, не как обязательное вето и не на пути keyboard hook.

## Что проверено на данном Windows 11

- Официальный COM-класс `SpellCheckerFactory`, интерфейсы
  `ISpellCheckerFactory.IsSupported`, `CreateSpellChecker`,
  `ISpellChecker.Check`, `IEnumSpellingError.Next`.
- На **данном компьютере** `ru-RU`, `en-US`, `he-IL` доступны. Примеры
  `привет` / `приввет`, `hello` / `helllo`, `שלום` / `שלללום` различаются
  верно. Нельзя переносить эту доступность на другие системы: нужна
  проверка на месте. `Check` возвращает *обнаруженные ошибки*, а отсутствие
  ошибок **не является положительным определением языка**.
- Испытуемый процесс не запускал TypeBridge.exe, не устанавливал hooks,
  не менял HKL, registry, словари Windows или пользовательские профили.
  Использовались только методы чтения COM. Исходные данные — штатные
  словари TypeBridge (не персональные) и синтетическая фиксированная
  клавиатура. Вход с настоящей клавиатуры **не исследовался**.

## Методика

Файлы:

- `experiments/windows_spellcheck_probe.py`: автономный COM probe.
- `experiments/windows_spellcheck_benchmark.py`: reproducible A/B; читает
  `data/` и штатные bundled v2 manifest, использует **настоящую** функцию
  решений `PolicyDecisionEngine.decide_token` с синтетическим `SyntheticMapper`.
- `experiments/test_windows_spellcheck_experiment.py`: три unit-теста
  таблиц клавиш, неизменности набора слов и перцентилей.
- `build/windows-spellcheck-research-detail-20261030.json`: машиночитаемый
  результат, сценарии и разбиение по шести направлениям.

Группы из **1 230** синтетических случаев:

| Группа | Число | Как устроена | Показатель |
|---|---:|---|---|
| Неверная раскладка | 420 | По 70 на каждое из 6 направлений; истинное слово отобрано из `confident`, исходная раскладка даёт неизвестную строку | Полнота исправлений |
| Известные слова | 300 | По 100 на язык из `confident` | Не переключать известный источник |
| Искусственные опечатки | 300 | По 100 на язык, повтор буквы внутри известного слова | Не переключать бессмысленный ввод |
| *Смоделированное* отсутствие в словаре | 210 | Половина положительных примеров, где слова **временно скрыты только от модели** через `WithheldWords` | Есть ли теоретический потенциал для нового источника |

**Существенное ограничение:** источником эталонных слов являются текущие
словари TypeBridge, а неверные раскладки и опечатки построены искусственно.
Такая выборка заведомо благоприятствует существующему движку; она не
доказывает его идеальную реальную точность. Искусственно скрытое слово —
не то же самое, что действительно отсутствующее в словаре новое слово.
Проверка не охватывает названия, личный ввод, длинные фразы, контекст,
IME, обработку реальных клавиш или пользовательские нестандартные HKL.

## Результат оценки решений

| Стратегия | 420 неверных раскладок: верно | 210 искусственно отсутствующих слов: верно | 600 контрольных примеров: ложных переключений |
|---|---:|---:|---:|
| Текущий TypeBridge | **420** | 0 (слова искусственно удалены) | 0 |
| Только Windows (исходное отклонено, один другой язык принят) | 363 | **179** | 0 |
| TypeBridge + обязательное Windows-вѐто | 363 | 0 | 0 |
| TypeBridge + Windows как *дополнительный* источник, без отмены решений TypeBridge | **420** | **179** | 0 |

Системный проверяющий отклонил **57 из 420** настоящих слов, которые
TypeBridge знает. В 300 известных исходных словах Windows не нашёл ошибок
лишь у **262**. Поэтому отсутствие ошибки Windows — полезный сигнал, но
**не источник истины** и не причина отвергать доверенное решение TypeBridge.

Разбивка Windows-only по направлениям: EN→HE **67/70**, EN→RU **64/70**,
HE→EN **52/70**, HE→RU **62/70**, RU→EN **51/70**, RU→HE **67/70**.
Контрольные 0 ложных переключений на таких простых сценариях **не доказывают**
безопасность правила rescue для реальных двусмысленных слов и опечаток.

## Латентность (из одного прогона)

Время мерилось только для `ISpellChecker.Check` плюс первое обращение к
возвращённому перечислителю ошибок. Создание COM-объекта, загрузка словарей,
планирование потоков, межпроцессная очередь, реальный typing/Hook и
перезапуск процесса не включены. Время *суммы трёх запросов на токен*:

| Показатель | Задержка |
|---|---:|
| p50 | 0.4832 мс |
| p95 | 0.8604 мс |
| p99 | 1.1093 мс |
| Максимум в опыте | 6.7362 мс |

В отдельности по RU / EN / HE p50 примерно **0.16 / 0.16 / 0.15 мс**,
p99 примерно **0.45 мс**. Проверено 1230 RU, 1230 EN и 1167 HE токенов;
некоторые HE-представления не состояли исключительно из букв и до вызова
Windows были отвергнуты нашим валидатором. Данные одного тёплого прогона
не являются жёсткой верхней границей и не доказывают deadline в 45 мс.

## Решение по архитектуре

1. **Не внедрять** синхронный COM-вызов в Hook, real-time No01 или
   переключение HKL до Space. Ни при каких таймаутах нельзя блокировать
   сам ввод.
2. При будущей разработке проверять `IsSupported(locale)` для каждого
   активного пакета, а соответствие BCP47 locale хранить декларативно.
   Для произвольных языковых пакетов R16/4 поддержку нельзя предполагать.
3. Вынести интерфейс в отдельный worker с собственным COM apartment,
   ограниченными очередями и version/generation-тегами. Поздний ответ
   **никогда** не должен изменять уже завершённое слово или HKL.
4. Сначала добавить *наблюдательный* shadow-mode поверх **синтетического**
   тестового набора. Для настоящего ввода нужен отдельный явно разрешённый
   этап приёмки с защитой паролей, исключениями и запретом сохранения текста.
5. До включения rescue в реальные исправления требуется независимый
   корпус фактических неизвестных слов, ошибок и ложных кандидатов,
   заранее определённые precision/recall, latency и fail-closed критерии.
   Не подменять эти критерии сегодняшними искусственно благоприятными данными.

**Вывод:** проверяющий Windows установлен и достаточно быстр для
асинхронного фонового *эксперимента*, но на этом корпусе нет оснований
менять текущие правила переключения. Обязательное вето определённо хуже;
дополнительное свидетельство для слов вне словаря перспективно, но требует
отдельного набора реальных контрпримеров и защиты от ошибочных переключений.

## Воспроизведение

```powershell
python experiments\windows_spellcheck_probe.py
python -m unittest discover -s experiments -p test_windows_spellcheck_experiment.py -v
python experiments\windows_spellcheck_benchmark.py --per-direction 70 --known-per-lang 100 --typo-per-lang 100 --output build\windows-spellcheck-research-new.json
```

Не перезаписывать существующий отчёт (скрипт специально отказывает при
существующем пути). Числа могут различаться между машинами и запусками.

Ссылки на Microsoft Learn: [ISpellCheckerFactory](https://learn.microsoft.com/en-us/windows/win32/api/spellcheck/nn-spellcheck-ispellcheckerfactory),
[ISpellChecker::Check](https://learn.microsoft.com/en-us/windows/win32/api/spellcheck/nf-spellcheck-ispellchecker-check).
