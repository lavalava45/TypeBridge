## Срочный остаточный дефект

Повторён только `current_word_packet_with_selection` из существующего audit
с модельными Win32/SendInput, без пользовательского ввода или clipboard.
У FrozenMapper числовые HKL приведены из сохранённого hex к int, иначе старый
диагностический helper не совместим с текущим контролем HKL.

При исходной строке `PREFIX ghbdtn SUFFIX`, активном выделении `ghbdtn`
и устаревшей памяти слова общий (не Scintilla) Pause снова вернул
`PRעינגאמ SUFFIX`; `prefix_preserved=false`, `suffix_preserved=true`.
Первая Backspace удаляет выделение, остальные — часть префикса.

Это актуальный модельный контрпример для неуведомлённого/программного
изменения выделения. Он не доказывает повреждение при каждом обычном
выделении мышью: mouse hook обычно сбрасывает память. Но закрывать P0-D
на основании успешного сценария Scintilla нельзя.

## Дополнение 07.11.2026 — P0-D: источник исправлен, физическая приёмка открыта

Исторический контрпример выше относится к предыдущим исходникам. Теперь
в generic-ветви `LiveHook._cycle_word` перед разрушительным
`manual_cycle_inputs` **не** используется одна лишь сохранённая память
последнего слова. Worker дважды подтверждает через текущий
`caret_word_recovery.read_caret_word`: выделение пусто, тот же UIA
Runtime ID и фокус, текст слова/физические клавиши/пробелы/позиция
каретки совпадают с предполагаемой заменой, исходные контекст/HKL
и поколение настроек не изменились. Второе чтение проводится после
проверки password guard, непосредственно перед первым `SendInput`;
изменение выделения во время guard тоже отменяет пакет. Восстановление
потерянного слова переиспользует уже проверенный исходный снимок,
поэтому дополнительного третьего процесса не создаёт. При отказе
никакой `Backspace`-пакет не отправляется, запасной путь и слепой
Undo отсутствуют, очередь и serial release-slot завершаются.

Повторный модельный контрпример:
`PREFIX ghbdtn SUFFIX` с выделенным `ghbdtn` и старой памятью
теперь остаётся неизменным; `prefix_preserved=true`,
`suffix_preserved=true`. Модель отдельно проверяет выбор, изменившийся
между снимками, другой идентификатор UIA с тем же текстом, отсутствие

без fallback на 2162. DPAPI clipboard recovery не менялся.

**Граница:** TextPattern — только читающая проверка состояния, не

полей. Если после последней проверки DOM меняется до обработки
`SendInput`, гонка R04 остаётся. Сохраняется политика
`explicit_password_only=True`; No01 и общая физическая приёмка R10

### Последующее минимальное усиление маршрутизации

`_use_native_text_transport` больше не доверяет одному флагу
`native_target=True`: класс и имя процесса повторно проходят
`native_field_metadata`, чтобы браузерный/WebView-контрол не попадал
в протокол адресной Win32-правки при ошибочных метаданных. Новые
регрессии проверяют настоящий RichEdit и имитированный браузерный
RichEdit с устаревшим флагом. `supports_native_edit` сейчас допускает
только `RichEdit50W`/`RichEditD2DPT`, **не** обычный Win32 `Edit`.
Добавление `Edit` без отдельной проверки замены, Undo/Redo и соседнего
текста не является безопасным минимальным fallback для TextPattern.
После этого усиления **119/119** целевых и **146/146** дополнительных
R04/Scintilla/браузерных mock-тестов — OK; `py_compile` и `git diff --check`
— OK. Физическая приёмка не проводилась.

Усиление не устраняет TOCTOU между последним чтением и глобальным
`SendInput`; **P0-D/R04 остаются BLOCKED/OPEN**. Не считать существующие
browser-TextPattern модели доказательством атомарной редакторской записи.

### Chrome ChatGPT: второй Pause после пробела (07.11.2026)

В физической проверке пользователя первый Pause на корректном RU-слове
после пробела сработал, а второй не сработал даже при паузе в три секунды.
Metadata-only `debug.log` показывает начатый `keyboard-worker` и затем
смену HKL RU → EN; для второго нажатия нет однозначного этапного события.
Это **не доказательство** ни занятости очереди, ни потери DOM-якоря.

Добавлены приватные `pipeline:manual-cycle` этапы: принятие горячей клавиши,
busy, смена revision, отсутствие слова, допуск восстановления, отказ UIA,
результат первой/повторной проверки TextPattern, отмена перед SendInput,
подтверждение HKL и доставка пакета. Новые значения — только фиксированные
коды состояний и миллисекунды, **никогда не текст, окно, клавиши, DOM или
Runtime ID**. Отдельный тест проверяет отсутствие утечек в debug.log,
модель Chrome — отказ второго Pause после неожиданной DOM-правки без записи.

Источником ощутимой задержки является два холодных запуска
`powershell.exe -STA` на один ручной Pause: измерено 675 и 770 мс в
безопасном пробном вызове на том же ПК (не в Chrome). Вторую проверку
нельзя просто убрать из-за P0-D; дальнейшая оптимизация требует постоянного
помощника с теми же проверками Runtime ID, выделения и текста.

Этот диагностический патч пока **только в исходниках**, запущенный Public
EXE не заменён. Он не считается исправлением браузерного Pause.
